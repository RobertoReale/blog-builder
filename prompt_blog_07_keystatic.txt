## FEATURE 06 — Keystatic CMS (GitHub mode)

The blog foundation and all previous features are already built.
Add Keystatic CMS so articles can be created and published directly from the browser
at `/keystatic`, without editing `.mdx` files manually.

When the user writes an article and clicks "Create" or "Save", Keystatic commits the
`.mdx` file to GitHub. Vercel detects the push and rebuilds the blog automatically.

CRITICAL INSTRUCTION: Before writing any code, use your web search tools to:
1. Find the current latest versions of `@keystatic/core`, `@keystatic/astro`, and `@astrojs/vercel`.
2. Check `@keystatic/astro`'s declared peer-dependency range for Astro. Compare it against the Astro major already installed in this project (check `package.json`). If the installed Astro major is OUTSIDE that range, stop before installing anything: downgrade the project's Astro version to the highest major that `@keystatic/astro` supports (Keystatic has historically lagged behind Astro's latest major by one or more versions), re-run `npm install`, and confirm `npm run build` still passes before continuing with this step. Note the pinned version and the reason in CLAUDE.md's STACK section. Do not attempt to proceed with an incompatible Astro major just to keep it "latest".
3. Verify the correct import path for the Vercel adapter (it changed between major versions — e.g. `@astrojs/vercel` vs `@astrojs/vercel/serverless`).
4. Check the current `keystatic.config.ts` field API (the `fields.*` and `collection()` signatures change across minor versions).
5. Search for known compatibility issues between the current Keystatic version and the current Astro version and Node.js version running on this machine (`node --version`).
6. Determine which version of `@astrojs/react` is compatible with the current Astro major version (major versions of `@astrojs/react` track Astro major versions — the major must match). Keystatic uses React for its admin UI and lists `@astrojs/react` as a peer dependency; npm v7+ will auto-install it at the latest version unless you pin it explicitly. Install the correct matching version based on your search result.
7. Verify the current Astro API for opting individual routes into server rendering. `output: 'hybrid'` was REMOVED in Astro 5 — it was merged into `output: 'static'`, with SSR opted into per-route via `export const prerender = false` on the specific route file. Confirm this is still accurate for the Astro major installed in this project (docs: https://docs.astro.build/en/guides/on-demand-rendering/) and adapt Step 2 below accordingly — do not blindly apply the `output: 'hybrid'` pattern shown as a reference below if your research shows it no longer exists.
8. Verify that Keystatic is still a maintained and recommended CMS for Astro static blogs with GitHub-based storage — if a clearly better alternative has emerged (actively maintained, similar capabilities, compatible with the current Astro static output), add a `<!-- ALTERNATIVE: <name> — <reason> -->` comment at the top of keystatic.config.ts, but implement Keystatic as specified.
If you encounter a bug you cannot resolve by reading the code, search for GitHub issues and community workarounds before giving up.
Your research findings always take precedence over any package versions, URLs, API signatures, or code patterns shown in this prompt. Treat all implementation examples as reference patterns — update them to match current reality based on what you find.

### Architecture note — two CLAUDE.md overrides

Keystatic GitHub mode requires server-side routes (OAuth callbacks, GitHub API proxy).
This step intentionally overrides two constraints from CLAUDE.md that were correct for
a fully static blog but must change for Keystatic:

1. Astro needs an adapter-backed way to run `/keystatic` and `/api/keystatic/*` as
   serverless functions while every other page stays statically pre-rendered. On
   Astro 5+ this means: keep `output: 'static'` and add `export const prerender = false`
   to Keystatic's own server routes only (Keystatic's integration handles this
   internally — you should not need to hand-write those routes). On Astro versions
   that still have `output: 'hybrid'` (Astro 3–4), use that mode instead. Use whichever
   API matches the Astro major actually installed (CRITICAL INSTRUCTION item 7) — do
   not mix the two.
2. "No @astrojs/vercel adapter" → must be installed (Vercel needs it to run the SSR routes)

These overrides are deliberate. All existing blog pages remain statically pre-rendered —
their behavior, performance, and deployment are completely unchanged. Only the
`/keystatic` admin UI and `/api/keystatic/*` backend routes run as serverless functions.
On Astro 5+, existing pages need no annotation at all (static is still the default per
route); do NOT add `export const prerender = false` to any existing page. On Astro 3–4's
`output: 'hybrid'`, `export const prerender = true` is implicit for all existing pages —
do NOT add that annotation to existing files either.

### Step 1 — Install packages

**Pre-flight check — Node.js version**

Run `node --version` before installing. Use the current active LTS version
(CRITICAL INSTRUCTION item 5 tells you which version to use). Avoid
end-of-life Node.js releases — they no longer receive security patches.

```bash
npm install @keystatic/core @keystatic/astro @astrojs/vercel @astrojs/react@<VERSION>
```

Replace `<VERSION>` with the version compatible with your current Astro major version,
as found in CRITICAL INSTRUCTION item 5 (e.g. `^5` if running Astro 5). Always install
it explicitly — do NOT omit it and let npm auto-install, or you may get an incompatible major version.

No dev-only flag — all four are runtime or build-time dependencies.

If the install fails with peer-dependency errors, retry with:
```bash
npm install @keystatic/core @keystatic/astro @astrojs/vercel @astrojs/react@<VERSION> --legacy-peer-deps
```

### Step 1.5 — Add a fallback dev script to package.json

If `npm run dev` fails after this step (which can happen on Node.js 22+ due to
the esbuild issue described above), users need an alternative. Add a `dev:build`
script to `package.json` that builds the site and serves the output statically:

Locate the `"scripts"` section in `package.json` and add:
```json
"dev:build": "npm run build && npx serve@latest .vercel/output/static -p 4321"
```

This lets users preview the blog locally even when `npm run dev` has issues.
Note: `dev:build` runs the full production build (slower, ~20s) but is 100%
reliable. Search also works here because `npm run build` runs Pagefind.

### Step 3 — Create keystatic.config.ts

Create `keystatic.config.ts` at the project root (same level as `astro.config.mjs`).
This schema mirrors `src/content/config.ts` field by field.

```ts
import { config, collection, fields } from '@keystatic/core'
import { wrapper, block } from '@keystatic/core/content-components'

// In development: write files directly to disk (no OAuth needed).
// In production (Vercel): commit via GitHub OAuth.
const storage: Parameters<typeof config>[0]['storage'] =
  process.env.NODE_ENV === 'development'
    ? { kind: 'local' }
    : {
        kind: 'github',
        repo: {
          owner: 'GITHUB_OWNER', // PLACEHOLDER — user must replace with their GitHub username/org
          name: 'GITHUB_REPO',   // PLACEHOLDER — user must replace with their repository name
        },
      }

export default config({
  storage,
  ui: {
    brand: { name: 'Blog Admin' },
  },
  collections: {
    articles: collection({
      label: 'Articles',
      slugField: 'title',
      path: 'src/content/articles/*',
      format: { contentField: 'content' },
      schema: {
        title: fields.slug({
          name: { label: 'Title' },
        }),
        date: fields.date({
          label: 'Date',
          validation: { isRequired: true },
        }),
        description: fields.text({
          label: 'Description',
          multiline: true,
          validation: { isRequired: true },
        }),
        tags: fields.array(
          fields.text({ label: 'Tag' }),
          {
            label: 'Tags',
            itemLabel: (props) => props.value || 'New tag',
          },
        ),
        status: fields.select({
          label: 'Status',
          options: [
            { label: 'Draft', value: 'draft' },
            { label: 'Published', value: 'published' },
          ],
          defaultValue: 'draft',
        }),
        language: fields.select({
          label: 'Language',
          options: [
            { label: 'English', value: 'en' },
            { label: 'Italian', value: 'it' },
          ],
          defaultValue: 'en',
        }),
        series: fields.text({
          label: 'Series',
          validation: { isRequired: false },
        }),
        part: fields.number({
          label: 'Part (in series)',
          validation: { isRequired: false },
        }),
        coverImage: fields.image({
          label: 'Cover Image',
          directory: 'public/images/articles',
          publicPath: '/images/articles/',
        }),
        sources: fields.array(
          fields.object({
            label: fields.text({ label: 'Label' }),
            href: fields.text({ label: 'URL' }),
          }),
          {
            label: 'Sources',
            itemLabel: props => props.fields.label.value,
          },
        ),
        content: fields.mdx({
          label: 'Content',
          components: {
            Callout: wrapper({
              label: 'Callout',
              description: 'An info or warning box with editable content',
              schema: {
                type: fields.select({
                  label: 'Type',
                  options: [
                    { label: 'Info', value: 'info' },
                    { label: 'Warning', value: 'warning' },
                  ],
                  defaultValue: 'info',
                }),
                title: fields.text({
                  label: 'Title',
                  validation: { isRequired: true },
                }),
              },
            }),
            ImageWithCaption: block({
              label: 'Image with Caption',
              schema: {
                src: fields.text({
                  label: 'Image path (e.g. /images/articles/photo.jpg)',
                  validation: { isRequired: true },
                }),
                alt: fields.text({
                  label: 'Alt text',
                  validation: { isRequired: true },
                }),
                caption: fields.text({
                  label: 'Caption',
                }),
                size: fields.select({
                  label: 'Size',
                  options: [
                    { label: 'Full width', value: 'full' },
                    { label: 'Half width', value: 'half' },
                  ],
                  defaultValue: 'full',
                }),
              },
            }),
          },
        }),
      },
    }),
  },
})
```

### Step 7 — Verify TypeScript compiles cleanly

Keystatic types are strict. Common pitfalls to avoid:

- `fields.number()` with `validation: { isRequired: false }` produces `number | null`
  in the output type. This is fine — the field is optional by design.
- `fields.text()` with `validation: { isRequired: false }` produces `string | null`.
  These match the Zod schema's `.optional()` fields (both accept absence of value).
- Do not use TypeScript `as` casts or `any` types anywhere in keystatic.config.ts.

Run `npm run build` and fix all TypeScript errors before marking this step done.
The build may produce output in `.vercel/output/` instead of `dist/` — this is correct.

### Step 9 — Usability review

Once the CMS is running, take a step back and make sure the writing experience
is actually well-made — clear, easy to use, and not invasive as the number of
articles grows.

Ask yourself: is every field obvious in its purpose? Do fields that grow over
time (like tags) stay manageable as the article count increases, or do they
become a burden? Does the cover image workflow feel natural, or does it require
manual steps that could be automated? Are the custom MDX components (Callout,
ImageWithCaption) usable as visual blocks inside the editor, or does the author
need to remember syntax by hand?

If you find issues, fix them. Common things to check:

- Tags: a dropdown with hardcoded options forces a config edit every time a
  new tag is needed — not sustainable. A free-form list where the author just
  types the tag is better.
- Cover image: a plain text path field is error-prone. A file picker that
  saves the image automatically and writes the correct path is better.
- MDX components: if custom components aren't registered in
  `fields.mdx({ components: { ... } })`, the author sees no visual block for
  them in the editor and must write raw MDX syntax by hand.

Do not add features beyond what is needed to make the existing CMS
experience genuinely usable. Fix what is broken or awkward; leave the rest
alone.
